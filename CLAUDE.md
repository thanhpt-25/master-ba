## Architecture (Phase 12 state)

Code lives in `src/masterba/`:
- `models/`: frozen Pydantic v2 models are the single source of truth; `schemas/*.schema.json` are generated from them and a test fails if they drift.
- `trace_store/`: file-based project store under `projects/<project_id>/`. Each business action is exactly one git commit (`commit_paths` commits only the files it wrote), and the store must run inside a git repo. `add_document` enforces the ID Stability Rule (a new version may not drop or revive item ids) and raises `IdStabilityError`.
- `trace_store/graph.py`: trace links point upstream to downstream; test case ids (`TC-...`) are aliases of their test item ref. `query_impact` and `rtm` walk only trace edges, not document containment edges.
- `rendering/`: JSON to `.xlsx`, no LLM. `catalog.py` is the single source for the 8 baseline templates; `shells.py` generates `templates/default/<TYPE>.xlsx` and `<TYPE>.template.json` from it (a test fails if the committed files drift). Bindings in `TemplateDefinition.cell_bindings` are parsed into typed models in `bindings.py` at load time. Output is byte-deterministic (`xlsxio.workbook_bytes` fixes zip timestamps), so re-rendering unchanged content makes no git commit. Every string is written as text, never as a formula.
- `llm/`: `LLM` protocol (`generate(system, user, output, tool_name)`), `AnthropicLLM` (forced tool call, key only from `ANTHROPIC_API_KEY`) and `FakeLLM`; every automated test uses the fake.
- `agents/requirements_analyst.py` + `agents/requirements-analyst.md` (prompt) + `skills/brd-from-intake/`: the model returns a `BrdDraft` without ids; `validate_draft` is the deterministic gate (citations in range, quote is a substring of the cited lines, unique titles), one retry, never repairs output.
- `team/`: Phase Team runtime. `Team` owns a `runs/RUN-####/` workspace (tasks, mailbox, token budget, escalations, single-writer check) and `run_writer_review` is the loop used by BRD and SRS: writer draft, deterministic gate (errors go back to the writer, no QA call), QA review, repeat up to `team_max_rounds` / `team_token_budget`, otherwise `escalated`. Summary, tasks and mailbox are committed once at the end; `transcripts/` and `checkpoint.json` are gitignored per run. Each round writes `checkpoint.json` (last validated drafts, feedback, upstream versions, tokens); `Team.reopen` + `pipeline/stage.open_team` resume an escalated run with the same run id (`--resume RUN-####`, commit subject ends `(resumed)`). Round limits per stage: `ProjectConfig.max_rounds_for(stage)`.
- `team/design_test_loop.py` + `agents/design_writer.py` + `agents/test_writer.py` + `pipeline/basic.py`: the Basic Design stage. Designer, tester and QA; a round is one cycle (designer, tester, gates, then QA reviews design and tests). The tester may question the designer (max 2 exchanges per cycle, mailbox `question`/`answer`); a question about an already answered item stops blocking and is reported as a customer question. On done it writes `DOC-BASIC_DESIGN-0001`, `DOC-TEST_IT-0001`, `DOC-TEST_ST-0001`, links (`realizes`, and `tests` for design item to TC-IT and SRS item to TC-ST) and renders all three; every design item has an IT case or an exclusion, every SRS item an ST case or an exclusion (`TestSpecContent.exclusions`).
- `agents/detail_writer.py`, `agents/unit_test_writer.py`, `pipeline/detail.py`: the Detail Design stage reuses `run_design_test_team` unchanged (Basic Design item to detail item `realizes`, detail item to `TC-UT` `tests`); `pipeline/stage.py` holds helpers shared by the pipelines.
- `change/`: Decision Records and propagation (`manual_gate`). `lifecycle.py` (new/approve/reject/close/from-run), `impact.py` (graph query, no LLM, documents in V order), `patch.py` (`RevisionPatch` with `update`/`add`/`remove`; pure `apply_patch` keeps untouched items identical and ids stable), `links.py` (links a document implies; links are never deleted), `reviser.py` + `agents/document-reviser.md` (the only LLM step), `propagate.py` (one writer+QA team run per affected document, new version `n+1`, progress file so a rerun resumes), `diffview.py`. CLI: `masterba dr new|from-run|approve|reject|propagate|close|list|show|diff`.
- `api/` + `frontend/`: the dashboard. `masterba serve --root DIR` runs a FastAPI app (`create_app(Settings)`) and the static web app (plain ES modules, no build step, CSP without inline script or style, text inserted only as text nodes). Local users in `.masterba/users.json` (PBKDF2, `masterba user add|list|remove`), signed session cookie, CSRF header `X-MasterBA`, roles viewer < approver < admin re-read on every request. Stage runs and DR propagation are background jobs (`jobs.py`, one per project, each written to `.masterba/jobs/<project>/<job>.json`; after a restart running jobs show as `interrupted`, 50 kept per project); `GET /api/health` is the only unauthenticated endpoint; every action calls the same library functions as the CLI, so git history is identical. Models come from the server environment only.
- `questions/`: the ledger of customer questions (spec 13). `Team` collects question drafts (writer, QA, tester) and QA's last blocking issues; `stage_result` records them after `team.finish` (`record_run_questions`: equal normalised text maps to the existing question, only stable references are stored, an escalated run adds at most 10 `qa_blocker` objections). `questions.answer` (imported directly, it needs `change`) makes `answer_question` create and approve a `clarification` DR; `confirmed_facts` lists decided clarification DRs (a rejected one is also `closed` but has no impact analysis, so it does not count) and every model call of a team carries them as a `<confirmed>` block (`RecordingLLM`). `Team.settle` lets only the first QA review of an artifact raise new blocking issues, and an `LLMOutputError` from a writer becomes gate feedback. CLI `masterba question list|show|answer|withdraw`, API `/api/projects/{pid}/questions`, dashboard Questions tab.
- `agents/qa_reviewer.py`: one stage-neutral reviewer; only `skills/qa-review/checklists/<stage>.toml` differs. The model returns issues only, the verdict is computed (`QaReport.passed`), severity is capped by the checklist, then `normalise_report` downgrades a blocking issue to advisory when it names no `action_required` or is a `customer_question` (the question goes to `TeamRun.customer_questions` and the stage's `open_questions`). `agents/srs_writer.py`: BRD to `SrsDraft` with coverage gate and open questions.
- `pipeline/brd.py` and `pipeline/srs.py`: `run_brd` / `run_srs` run the team, then (only if done) assign ids in code, write requirements/document/trace links, render, commit the run record. Nothing business-related is written on escalation. Both refuse when the document already exists.
- `cli.py`: `masterba init-project [--language ja|en]` (default `ja`; sets `ProjectConfig.document_language`, the language of generated content), `masterba run brd --project PRJ-001 --input file.txt` and `masterba run srs --project PRJ-001` and `masterba run basic --project PRJ-001` and `masterba run detail --project PRJ-001` (extra `--test-model`), all with `--model` / `--qa-model` (a stronger separate QA model is recommended) and `--resume RUN-#### [--rounds N]`; `init-project --rounds basic=6` sets a per-stage limit; `masterba doctor [--init]` checks git, work tree, templates, state and model key; exit code 3 means escalated (installed console script; `--root` is the git work tree, default cwd). Live-model test: `uv run pytest -m live` with `ANTHROPIC_API_KEY` (an Anthropic-compatible gateway works via `ANTHROPIC_BASE_URL` and `MASTERBA_MODEL`). `MASTERBA_REQUEST_TIMEOUT` / `MASTERBA_MAX_TOKENS` set the request limits; a failed model request (not a configuration error) escalates the run with a checkpoint instead of raising (spec 11 section 1.6). Every model call carries `<confirmed>` facts and `<open_questions>` from the ledger; no stage may state an answer to an open question (spec 13 section 5.1). Full-run example intake: `tests/fixtures/intake/timesheet_ja.md`.
- `diff/`: structural diff by stable item id plus `classify_change` (pure similarity, no LLM; numeric edits always count as structural).

- `knowledge/` (spec 12, `docs/architecture/08-knowledge-base.md`): per-project knowledge base under `projects/<id>/knowledge/` (only `manifest.json` is committed; `sources/`, `index/`, `.lock` are gitignored, with an `info/exclude` fallback). `store.py` (add/replace/remove/list, one `kb(P): ...` commit each, rollback on failure), `safety.py` (`check_upload`), `extract/` (md, txt, xlsx, docx, pdf to chunks `KB-####` + `#chunk.n`), `keyword.py` (FTS5 over bigram hex tokens), optional `embedder.py` / `vectors.py` (rag extra: sentence-transformers + LanceDB, imported only inside functions), `indexer.py` (generations behind `index/CURRENT`), `retriever.py` (RRF hybrid, keyword-only fallback, `FakeRetriever`), `reference.py` (escaped `<knowledge>` block), `citations.py` (citation gate), `session.py` (`open_session` before `Team.open`; per-role blocks reused by QA; seen refs kept in the checkpoint), `trace.py` + `proposal.py` (Knowledge_Nodes, `derives_from` links in the document commit, `knowledge_change` DR on replace/remove of a cited source; `proposal` is imported only by CLI and API). Every pipeline takes `knowledge=` (default `open_session`); tests pass a session over a `FakeRetriever`. CLI `masterba kb ...` lives in `cli_kb.py`; API `/api/projects/{pid}/knowledge`; dashboard Knowledge tab. `uv run python -m masterba.knowledge.evaluation` and `pytest -m rag_eval` need the extra and a model from `masterba kb setup`.
- `review/` (spec 15): phase review gates. `gates.py` (imported by the pipelines: `STAGE_DOCS`, `phase_state`, `require_reviewed`, `initial_status`) and `actions.py` (imported by CLI and API only, it needs `change`: `approve_phase`, `reject_phase`). With `ProjectConfig.review_gates` (true for new projects, false for old `project.json`), a `done` stage stores its documents `in_review`, and srs, basic and detail refuse to start while the previous phase is `in_review`. Approve writes `reviews/REV-####.json` and sets `approved` in one commit, then renders the workbooks again (they print the status). Reject creates and approves a `review_feedback` DR whose propagation writes version n+1 `in_review` and sets version n `superseded`; `set_document_status` changes only `document.status` of a stored version. CLI `masterba review status|list|approve|reject`, API `GET /reviews`, `POST /stages/{stage}/approve|reject`, Approve and Reject on the overview cards.
- `calibration/`: sample `.xlsx` -> profile -> heuristic (JA/EN label synonyms) -> optional model refinement -> validated `MappingDraft` -> company template under `templates/companies/<company>/`. A calibrated template is ignored by `resolve_template` until `<TYPE>.confirmed` exists; CLI `masterba template ...`, admin-only API `/api/templates`, dashboard Templates view.
- Containers: `Dockerfile` (uv builder, slim runtime with git, non-root `masterba`, source kept at `/app` as an editable install because prompts, skills, templates and the web app are found relative to it) and `compose.yaml` (one service, work tree bind-mounted at `/work`, port on 127.0.0.1 only, keys from a gitignored `.env`). Git author may come from `GIT_AUTHOR_*` variables instead of git config. CI: `.github/workflows/ci.yml`.

## Intended purpose

Based on direction from the repository owner, this project will house a multi-agent system that generates and maintains Japanese-SIer-style V-Waterfall (IPA-defined) deliverables:

- Customer requirements → BRD (業務要件定義書) / SRS (システム要件定義書)
- BRD/SRS → Basic Design (基本設計書) + Basic Test Design (結合テスト仕様書 etc.)
- Basic Design → Detail Design (詳細設計書) + Detail Test Design (単体テスト仕様書)

Deliverables are Excel workbooks following per-company templates, defaulting to standard Japanese SIer templates when no company-specific template is specified. Changes to requirements or design must be tracked via a decision-record mechanism that propagates updates to dependent documents (traceability across the V-model).

How the system works as built (layers, data model and storage, per-stage data flow, team-runtime control flow, change management, interfaces and deployment) is described in `docs/architecture/` (start at its `README.md`); update the matching document when you change a flow it describes. A full concept design for this agent system is tracked in `docs/concept-design.md`, and the phased implementation plan (spec-driven development: spec → plan → tasks → implement → validate per phase) is tracked in `docs/roadmap-phases.md`. Per-phase specs will live under `specs/`, starting with `specs/00-constitution.md`.
